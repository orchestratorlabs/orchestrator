========================================
DESCRIPTION
========================================
This registry file acts as the master index for OrchestratoR accessibility RAG documents.

It does not replace individual component RAG files.
Instead, it tells the LLM:
- which RAG file applies to which component
- which file is the primary rule set
- when a component-specific extension should be used
- how component scoring should inherit or extend other scoring models

This registry supports a scalable Retrieval-Augmented Generation workflow for accessibility health scoring across multiple UI components.

========================================
INTENDED USE
========================================
Use this registry before evaluating a UI component.

Workflow:
1. Identify the component type being evaluated
2. Retrieve the matching component RAG file
3. Apply the component-specific scoring and rule logic
4. If a component extends another base component, preserve the base logic where applicable
5. Return the accessibility health score, findings, severity, and recommended fixes

========================================
RETRIEVAL RULES
========================================
Use the Button RAG when:
- the user submits a standalone button component
- the evaluation target is specifically the button itself
- the request focuses on button semantics, states, or interaction behavior

Use the Card RAG when:
- the user submits a Card component with nested content
- the request concerns the accessibility of the full Card UI
- the Card includes image, text, and button or other interactive children

Use both Button and Card RAG files together when:
- the Card contains a nested button that must also be independently evaluated
- the overall Card score depends partly on the quality of the nested button implementation
- a developer or engineer needs both component-level and nested-control findings

========================================
SCORING GOVERNANCE
========================================
Registry rule:
A composite component may inherit relevant scoring logic from a base component RAG, but it must add its own component-specific rules rather than reusing the base score unchanged.

Implication:
- Button score alone is not sufficient for Card evaluation
- Card score should reflect both container-level accessibility and nested control quality
- Unknown evidence should remain Unknown rather than being assumed Pass

========================================
LLM INSTRUCTION
========================================
When using this registry:
1. Identify the component type first
2. Retrieve the most specific matching RAG file
3. Use dependency relationships when a component extends another component's logic
4. Do not merge unrelated rule packs
5. Do not invent requirements not supported by the selected RAG files
6. If multiple RAG files apply, prioritize the more specific component RAG while preserving relevant base rules

========================================
SIMPLE EXPLANATION
========================================
The individual RAG files contain the rules.
This registry tells OrchestratoR which rule file to use.

Example:
- Button request -> retrieve orchestrator_button_health_score_rag.txt
- Card request -> retrieve orchestrator_card_health_score_rag.txt
- Card with nested button -> retrieve Card rules first, then preserve relevant Button rules
